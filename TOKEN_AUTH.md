# Task 06 — database-backed software token

The existing Task 06 sector now uses `/api/portal/token/*` and the college account database. No additional dashboard or new secret environment variable is needed. Existing grade authorization and lab-policy controls are unchanged; token permissions are deliberately **not** controlled by the educational grade-policy switches.

## Flow and permissions

- Student signup creates a known database identity but **no portal session**. Student password sign-in also creates no portal session. Both issue a random, five-minute pending ticket; only its SHA-256 hash is stored. The cookie is HttpOnly, SameSite Strict, and Secure in cloud mode.
- The existing college sign-in card shows a PIN/passphrase step. For a first token, it enrolls and then verifies a fresh challenge; only a successful verification consumes the pending ticket and establishes that student's portal session. Refreshing the page resumes an unexpired pending step. Expired pending steps require password sign-in again.
- Task 06 can also complete the pending flow. Open the sector from the college card, refresh accounts, enroll if needed, issue a challenge, then verify. Return to College / refresh after success.
- Administrators see their own account and all active student accounts in the sector. They can provision a student's first token and demonstrate challenge verification for that student. **A signed-in demonstration never creates or replaces a session**, even for an administrator selecting a student. A student/professor sees only their own account and cannot select another identity, even by crafting JSON.
- Professor self-signup remains permitted, and professor/admin password login remains unchanged. Self-signup still cannot create an administrator. Role changes revoke affected pending tickets/challenges as well as the existing session revocation.
- Enrollment is first-token only. There is no reset/revoke/unlock API in this release. A locked token cannot be replaced by enrolling again. Recovery is an explicit database-operator procedure, not an anonymous or student endpoint.

## Cryptography and transaction boundaries

RSA-2048 keys are generated by `cryptography`. PostgreSQL persists the public PEM, **PIN/passphrase-encrypted PKCS #8** private PEM, scrypt PIN hash (Werkzeug default), failure count, and status. No plaintext private key or PIN is persisted or returned. A key is decrypted transiently only during a PIN-verified signing operation. RSA-PSS/SHA-256 signs a random challenge and verifies with the enrolled public key. Altered-challenge and wrong-public-key demonstrations actually run cryptographic verification and fail.

This is a **server-side software-token simulation**, not smart-card isolation, PKCS #11, phishing-resistant MFA, or proof of hardware possession. A stolen database permits offline guessing of short PINs against the encrypted key/hash; choose long disposable passphrases. Database operators / application compromise are outside this educational trust boundary. TLS and protected DB access are essential. Do not use real student information or production credentials.

Challenges live for 60 seconds and are bound to both target identity and either the exact authenticated session hash or password-verified pending-ticket hash. Atomic `DELETE ... RETURNING` consumes a challenge before checking PIN/signature, committing even on a normal rejection. User-row locks serialize first enrollment and operations; token-row locks serialize persistent failure counts. Five rejected PIN/signature attempts lock the token across workers/restarts. Replay, altered data, wrong key, expired challenges, expired pending tickets and cross-context requests are rejected. Endpoint data never trusts a submitted identity without authorization. All POST endpoints retain existing CSRF checks. Audit events contain account IDs/actions/outcomes, never PINs/private keys/tickets. Expired records are rejected regardless of cleanup. Operators may periodically delete expired pending tickets/challenges as database maintenance. New password sign-ins supersede earlier tickets for the same user.

The old `/api/tasks/authentication/run` is retained solely for old local teaching tests, explicitly labeled `legacySimulation: true`, `portalAuthentication: false`, and deprecated in its response. Its per-lab memory/files have **no imports or access path to portal identity/token tables**, and it cannot issue portal sessions. The current UI no longer calls it.

## Automatic additive setup and deployment

The existing backend database connection automatically checks token schema version 3 before serving DB-backed operations. A transaction-scoped PostgreSQL advisory lock and a second version check serialize simultaneous worker cold starts. It creates only the four new token tables (and their indexes), then inserts a schema version marker in the same transaction. It does not alter base tables, remove accounts, grades or sessions, and exposes no public migration endpoint. There is no process cache that could incorrectly remember rolled-back DDL. The validated configured schema/search_path is honored, including isolated test schemas.

The fourth table, token_verified_sessions, records provenance only for successfully token-verified student sessions. Existing password-only student sessions are left untouched in storage but cannot authorize portal access; staff sessions work unchanged. Thus enabling token requirements needs no destructive cleanup of existing records.

Deploy the changed Python, HTML and JS files together. The deployed backend reuses its existing ENIGMA_DATABASE_URL or DATABASE_URL; no new secret is needed. Its DB role must have CREATE in the existing portal schema plus normal table/index/sequence privileges. If the deployment intentionally forbids runtime DDL, an authorized operator can instead apply database/schema.sql (or run python scripts/setup_portal.py) first; subsequent requests only read the version marker. Missing base schema is not bootstrapped by this helper. A DB permission/availability failure returns the existing generic 503 rather than exposing connection details.

After deployment verify staff access, student pending signup/sign-in, enrollment and verification, then admin student selection and unchanged administrator session identity. Full hosted DB/browser smoke testing is still necessary.

## Tests

Run `uv run --no-project --with-requirements requirements.txt python -m unittest discover -s tests -v` (or ordinary Python after installing requirements). `tests/test_token_auth.py` uses a strict SQL fake with real RSA/key encryption/signatures and API authorization tests. It does **not** prove PostgreSQL concurrency. `tests/test_portal.py` adds opt-in real-PostgreSQL tests, including concurrent consumption from two connections, expiry, ciphertext storage, lockout, and password-only pending restrictions. Set `ENIGMA_TEST_DATABASE_URL` to a **disposable test database** to run those; they create/drop a unique schema. Never aim tests at production.

Manual browser/database smoke testing is still required before publishing; mock/unit tests cannot verify a hosted database's permissions, deployed schema, or the complete live browser interaction.

## Demonstration token number in Local Storage

After successful authentication, the college frontend saves `enigma_token_id` in the site's Local Storage. View it in browser DevTools → Application → Local Storage → the college site's origin. This decimal string is the full SHA-256 fingerprint of the enrolled software token's stored public PEM, converted to base 10. It identifies the existing software token; it is **not** a session token, PIN, private key, or credential. Treat it as a string (up to 78 digits), not a JavaScript Number. It is stable across sign-outs, logins and refreshes while the enrolled key is unchanged, including accounts enrolled before this feature. No database migration is required.

Only the authenticated account's identifier is included as `tokenId` in successful authentication/session responses. Password-only pending verification does not expose it. Accounts without an enrolled software token have no Local Storage entry. Successful sign-out and detected session loss remove the browser copy; the database enrollment remains, so the same number returns on the next successful login. Browser storage failures do not block authentication. Editing or copying this identifier grants no access: the existing HttpOnly session cookie, PIN challenge and server-side authorization are unchanged.
